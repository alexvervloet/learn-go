# grpc-concepts

The four RPC patterns, the three things gRPC does that HTTP does not, and the mistakes each one invites.
4,610 lines, and every number here was measured.

## Running it

```sh
go test ./...
```

No services, no Docker, no network: every test runs against an in-process server on
[bufconn](https://pkg.go.dev/google.golang.org/grpc/test/bufconn), which is an in-memory `net.Listener`. The
whole suite is under a second.

Regenerating the stubs needs the protobuf toolchain, and they are committed so a reader does not:

```sh
brew install protobuf
go install google.golang.org/protobuf/cmd/protoc-gen-go@latest
go install google.golang.org/grpc/cmd/protoc-gen-go-grpc@latest

./generate.sh
```

## Why the generated code is committed

The rule for a private service is "regenerate, do not commit". The rule for a repo someone clones is the
opposite, and the reasoning is in the repo's [.gitignore](../../../.gitignore) where the next person to touch it
will read it. In short: `git clone && go build ./...` has to work with nothing but a Go toolchain, and with the
stubs ignored it needs protoc plus two plugins plus matching versions before the first line compiles.

CI regenerates and diffs, so a stale stub fails the build rather than going unnoticed.

## The four patterns

```
unary          client ──req──> server ──res──> client
server stream  client ──req──> server ──res──res──res──> client
client stream  client ──req──req──req──> server ──res──> client
bidirectional  client <──req──res──req──res──> server   (both at once, independently)
```

What changes in the generated Go is more than it sounds. A unary method looks like a function call. A
server-streaming method takes a stream and returns only an error. A client-streaming server's `Recv` ends with
`io.EOF`, which is the one place gRPC's Go API uses an error value to mean success. And bidirectional needs a
goroutine per direction or it deadlocks, which the tests demonstrate by writing the deadlocking version and
watching a client time out on it.

## What the measurements said

An M2 Max, Go 1.27, grpc-go 1.84.

### Protobuf against JSON

A `Price` message: a symbol, a price in cents, a timestamp and a sequence number.

| encoding | bytes | marshal | unmarshal |
| --- | --- | --- | --- |
| protobuf | **25** | 107ns, 1 alloc | 141ns, 3 allocs |
| `encoding/json` | 102 | 305ns, 1 alloc | 541ns, 2 allocs |
| `protojson` | 98 | 842ns, 16 allocs | |

**4.1x smaller and 2.9x faster to encode** than `encoding/json` on the same struct. The size ratio is the one
that matters at scale, because it is bytes on every wire and in every log.

`protojson` is the canonical JSON mapping, which is what a gRPC gateway emits: camelCase names, an RFC 3339
timestamp, and int64 rendered as a STRING because JavaScript numbers cannot hold one. It is 7.9x slower than
protobuf and 2.8x slower than `encoding/json`, which is worth knowing before putting a gateway in front of
everything.

### The transport

| | per unary call |
| --- | --- |
| bufconn (in memory) | 26.6µs |
| loopback TCP | 69.8µs |

**2.6x**, and that gap is the socket and the kernel with no network at all. A real network adds its round trip
on top of both, which is why the interesting optimisation is almost never the encoding.

**Interceptors are free.** No interceptors 27.9µs, one 26.4µs, six 26.0µs: all within the noise of a 26µs call.
A chain of six costs less than measurement error, so the argument against middleware in gRPC is not a
performance one.

### Streaming against chattiness

100 messages, one stream against 100 unary calls:

| | time | allocated |
| --- | --- | --- |
| one stream | **127µs** | 97 KB |
| 100 unary calls | 2,891µs | 1,247 KB |

**22.7x faster and 12.9x less garbage.** A stream amortises the framing, the headers and the status trailer over
every message. Which means a chatty API is the thing to fix before the transport, and it is the same finding as
the N+1 measurement in database-concepts arrived at from a different direction.

## The three things that are different from HTTP

### Deadlines propagate

A client's deadline becomes the server's context deadline. Nothing configures this: gRPC sends it as the
`grpc-timeout` header and the server applies it. `TestDeadlinePropagates` shows a stream ending with
`DeadlineExceeded` after five ticks because the client gave it 120ms, and the server never mentioned a timeout.

That is the mechanism that makes a mesh-wide timeout budget possible, and it is why a call with NO deadline is
a bug: it can hang forever, and in a mesh one slow service then holds connections everywhere.

### Errors are codes, not statuses

`codes.NotFound` is not 404. There are seventeen codes and mapping them to HTTP is a gateway's job.

The one that catches people: returning a plain `errors.New` from a handler gives the client `codes.Unknown`,
which it cannot act on. It cannot tell a bug from a bad request from a transient failure, so it either retries
everything or nothing.

Errors also carry structured DETAILS, which HTTP has no equivalent for. `errdetails.BadRequest` with
`FieldViolations` says which fields were wrong; `errdetails.RetryInfo` says how long to wait. Using the standard
types rather than your own means a generic client can render them.

### Metadata is headers and trailers

Headers go before the response and trailers after, and the difference is not cosmetic: anything computed during
the call (a duration, a row count, a cache status) can only be a trailer. `grpc.SetHeader` fails if called after
the first `Send`; `SetTrailer` has no such window.

**Keys are lower-cased**, because HTTP/2 requires it. `md.Get("Authorization")` works because Get lower-cases
what you pass it. `md["Authorization"]` returns nothing, always, and an auth interceptor written that way
rejects every request with a reason that is invisible in the code. The test builds both and shows one rejecting
a valid call.

## The traps, each demonstrated

**A streaming server that does not check its context streams forever.** The client hangs up, the server's
context is cancelled, and a server that does not `select` on `Done()` keeps producing. It does not show up in
testing because tests do not usually hang up mid-stream. `TestCancellingAStreamStopsTheServer` does, and asserts
the server stopped within a few ticks.

**A bidirectional server that reads before writing deadlocks a request-response client.** Neither side is wrong
on its own: the server reads until EOF, the client waits for a reply before closing, and they wait for each
other. The test runs the broken server with a 300ms deadline and watches it expire. The correct version uses a
goroutine per direction and sends an unprompted message after the client has stopped, which is what independent
directions means.

**`io.EOF` from `Recv` is success, not failure.** It is how a client stream ends. Code that treats every `Recv`
error as a failure rejects every successful upload. The check has to be `errors.Is(err, io.EOF)` first.

**A panic kills the process, not the call.** grpc-go does not recover, deliberately. A service without a
recovery interceptor is one nil map away from restarting, and every in-flight call on every stream dies with it.
And the recovery interceptor has to exist TWICE, once unary and once streaming, because gRPC has four middleware
shapes where HTTP has one.

**`DeadlineExceeded` is not retryable by default.** The call MAY have happened. Retrying a non-idempotent call
that timed out is how you charge a card twice. The default set is `Unavailable` and `ResourceExhausted`, and an
interceptor that retries everything is worse than one that retries nothing.

## Schema decisions that are expensive to change

The `.proto` files carry these as comments; here is the summary.

**Field NUMBERS are the wire format, names are not.** Renaming a field is free and renumbering one is a silent
incompatibility. Numbers 1 to 15 encode their tag in one byte, so the fields on every message go first.

**`reserved` is what a deleted field leaves behind.** Without it the next person reuses the number and an old
client decodes the new field as the deleted one. It costs one line.

**`optional` in proto3 makes presence detectable.** The generated Go type becomes a pointer, so `nil` and `""`
are different and "clear this field" can be expressed. The tests show two requests that differ only in whether
`nickname` was set and produce different replies.

**proto3 has no required fields**, so an empty message is valid and validation is entirely the server's job. A
schema cannot express "name is required".

**Money is an integer of the smallest unit.** protobuf offers `double` and it is the wrong type for money in
any language.

**`google.protobuf.Timestamp`, not an int64.** It carries nanoseconds, renders as RFC 3339 in JSON, and maps to
a native time type in every language. An int64 named `timestamp` is a unit nobody documented.

**The version goes in the PACKAGE.** A breaking change means a new package served alongside the old one, because
the wire format has no version negotiation: a v1 client and a v2 server decode each other's bytes into the wrong
fields and report success.

## Testing gRPC

`bufconn` is the right default: in-memory, no port, no TLS, works in a sandbox with no network. It does not
exercise connection establishment, TLS, keepalives, load balancing or DNS, so a suite should have a couple of
tests on a real listener. `grpctest.Options.RealListener` switches between them and the benchmark above measures
what the difference costs.

Two details in the harness are worth copying:

- `grpc.NewClient`, not `grpc.Dial`, which is deprecated as of 1.63 because it did a blocking connect by default
  and its name promised a connection it did not always make.
- The target is `passthrough:///bufnet`, not `bufnet`. `NewClient` defaults to the DNS resolver and would try to
  resolve the name; `passthrough` hands it to the dialer unchanged. Without it a bufconn test fails with a DNS
  error that says nothing about bufconn.

And the embedded `UnimplementedXServer` in every service implementation is a real decision, not boilerplate.
With it, adding a method to the `.proto` leaves the server compiling and the new method returns
`codes.Unimplemented`. Without it, adding a method breaks the build. Which is right depends on who owns the
schema: for a proto owned elsewhere, embedding is the only way to deploy at all; for one you own, a build
failure is the better outcome.

## Things worth stealing from here

- `grpctest.Start` and `Dial`: bufconn or a real listener, interceptors chained, `GracefulStop` with a deadline
  and a fallback to `Stop` for the stream nobody closed.
- `interceptors.countingServerStream`: the wrapping a streaming interceptor needs to see messages rather than
  just streams, which is why so many only count streams.
- `interceptors.RetryUnary`: retries only the codes that are safe, bounds the backoff by the context, and says
  in its doc comment why `DeadlineExceeded` is not in the list.
- `server.Chat`: the correct bidirectional shape and the deadlocking one, side by side, with the joining of the
  two goroutines written out.
